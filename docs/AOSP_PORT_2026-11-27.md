# Custom Android feasibility: NL5H00X_TP, 2026-11-27

The stock [Android 9 audit](ANDROID_REA_2026-11-27.md) identifies the build. This follow-up asks whether a replacement system could retain panel output, HDMI input and the remote. Keep the kernel and vendor stack as the starting hypothesis for an Android 9 board port. Do not treat a generic GSI as a verified replacement. No candidate image was compared, booted or flashed; no root, UART or reboot was used.

## System and display baseline (read-only ADB)

`ro.treble.enabled=false`, `ro.vndk.version=28`, `ro.vndk.lite=true`, `ro.zygote=zygote32`, `ro.product.cpu.abilist=armeabi-v7a,armeabi`, `ro.build.system_root_image=true`. These describe the shipped userspace, not the CPU's maximum capability. The slot suffix, verified boot state, flash lock and OEM unlock support properties queried returned empty values. They do not establish an unlocked bootloader or a supported route to run another image.

The device VINTF manifest (target level 2) declares graphics composer 2.1, 32-bit passthrough; TV input 1.0 via hwbinder; and HiSilicon display and TV middleware. SurfaceFlinger reported ARM Mali-450 MP, OpenGL ES 2.0. The library inventory included the Mali EGL implementation and bigfish composer/gralloc modules. Finding a module does not prove it was loaded.

The legacy linker section covers executables under `/system`, `/vendor`, `/odm` and `/sbin`. Its default namespace is not isolated and searches `/system/${LIB}`, `/vendor/${LIB}`, then `/odm/${LIB}`. The postinstall section is separate. Direct process executable inspection was denied as shell; do not infer which duplicate library a running process mapped.

A replacement system must make compatible symbols visible to the consuming process. Retaining vendor alone, matching filenames, or rendering the Android home screen does not demonstrate HDMI compatibility.

## HDMI from registration to a video surface

**Manifest and running system.** REA found required Leanback and live TV features in `com.hisilicon.tvinput.external` (min/target API 28). The stock APK is under `/system/app/HiExternalTvInput`, not vendor. ADB showed grants for TV input hardware, HDMI CEC, secure settings and the HiSilicon common permission. The TV input manager listed three logical HDMI inputs for `HiHdmiTvInputService`, with hardware port IDs 1 through 3. This is not a physical connector count or evidence of active video.

**Code provenance.** The original APK SHA-256 is `474042790c89e66ae7d624dca84e67d7f484c56c8ee05534f76764eab4caf3b3`. REA could read its manifest but did not resolve the service class from that APK alone. The ARM VDEX SHA-256 `635aa4ab48426ff1f05f8520673de5df09d47a9b59a83b4b1e76224c599f5fb0` matched on the projector and on the host. Offline extraction and CompactDex conversion yielded a DEX with 768 classes. REA inspected a separate APK copy with that DEX (SHA-256 `aa21010e87cf524ad8f2a2c4b5ad15f1844a69e2471f15e7f28735dd7ee19f4d`); it was never installed. Private evidence IDs and binaries are not included.

**Decoded REA methods** (static observations, not a signal capture):

1. `HiHdmiTvInputService.onCreate()` obtains `tv_input` and `hdmi_control`, registers callbacks when available and calls `checkDBConfig()`. That method reads CEC settings and `HitvManager.getHdmiCEC().getUIStatus(3)` for logging; it catches `Exception`. This alone does not make a CEC failure fatal to video.
2. `onHardwareAdded()` rejects null, non-type-9 and already-seen HDMI ports. It builds `TvInputInfo` for `HDMI<n>` and maps hardware, port and input identifiers. Registration is separate from tuning.
3. `HdmiSessionImpl.onTune()` selects sources 9, 10, 11 or 12 for logical ports 1, 2, 3 or 4 using `SourceManager.selectSource(source, 0)`. An unrecognized port returns false. The method also sets the video window and calls `hdmiSelectByPort`. Four code branches do not imply four physical ports.
4. `onSetSurface()` caches the Android `Surface`. When source selection is enabled, the surface exists and display has not yet been enabled, it calls `HitvManager.getSourceManager().setVideoDisplay(surface)`. It returns true even when it merely cached the surface.
5. `notifyMessage()` handles the other arrival order. Source-selection completion (65543) enables selection and attaches a cached non-null surface. Signal status (65538) reads the status from the parcel and can also attach the surface. Status 0 reads timing, emits `TIMING_CHANGED` and reports video available; status 3 reports unstable video and schedules a check after 1500 ms. Framework notifications do not measure pixels on the panel.

## Where source selection and surface attachment enter JNI

REA located `SourceManagerImpl` in the bytecode recovered from stock `HitvShare.vdex`. Its on-device and offline SHA-256 matched (`4f9053425305bb36e04b233fd8ae744f82bafe1641e8bc2e5722ad024f5014fb`); the converted DEX has SHA-256 `a6da9a307fafecc6f103cc0f5a6f781eb11719162b7c7547bc090a12dfdf0b4b`. The two calls from the HDMI session follow different paths:

- `selectSource(int, int)` calls the three-argument overload with a final `-1`. That overload writes `CMD_SOURCE_SELECTSOURCE`, source ID, window and channel ID into a `Parcel`. It returns the result of `HitvManager.invoke`, which delegates to `native_invoke`.
- `setVideoDisplay(Surface)` returns `-1` for a null or invalid surface. Otherwise it calls `HitvManager.native_setVideoDisplay(surface)` and returns `0` if the call returns normally. That value is not confirmation of a displayed frame. The session's `onSetSurface` does not propagate the wrapper's status.

The `HitvManager` class initializer loads `hi_tv_jni` and calls `native_init`. ADB confirmed `/system/lib/libhi_tv_jni.so` (SHA-256 `8086e121db1eecde171c934f68f413f440c94f46e8b7cf9b6b4f33f1e1337787`). A port retaining the stock Java stack therefore needs a compatible JNI library visible to it. The Java trace does not identify the native service receiving the selection request or prove that it displayed video.

**How events reach Java listeners (REA).** `HitvManager.postEventFromNative` puts the event ID, two integer arguments and the `Parcel` into an Android `Message` and queues it on `mEventHandler`. If the handler is null, the method logs an error instead. `HitvManager.EventHandler.handleMessage` looks up listeners by `message.what` and calls `ITVListener.notifyMessage(what, arg1, arg2, parcel)` on each entry. Thus source-selection completion (65543) and signal status (65538) have separate listener lookups. Port compatibility requires preserving the event IDs and parcel contents, not just the method signature. This traces delivery from the Java entry point; it does not establish which native producer calls it or which events occurred on the projector.

**Next offline check:** identify the native bindings for the two outgoing calls and the native producer of the callback. For a specific candidate, compare its framework APIs, linker visibility, exported native symbols and vendor service registrations to this stock baseline. An authorized boot path, successful boot, physical HDMI output and remote behavior on a replacement image remain unverified.
