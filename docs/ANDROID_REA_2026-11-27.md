# Android 9 on the NL5H00X: 2026-11-27 observations

This report maps Android 9 on one modified NL5H00X_TP, from board startup and HOME selection to the interfaces used for projection, input, audio and video. Start with the [device-wide findings and open questions](#device-wide-coverage-and-open-questions).

- **How Android starts:** [board and init configuration](#board-identity-and-android-startup-configuration), [build and storage](#build-and-storage-adb), [HOME selection](#two-home-decisions).
- **How apps reach projector hardware:** [display and framebuffer](#display-mode-ui-density-and-framebuffer), [TV inputs](#tv-framework-personality-and-input-inventory), [focus motor](#focus-motor-request-versus-on-screen-feedback), [keystone controls](#which-keystone-settings-screen-opens), [sensors](#sensors-exposed-to-android-apps).
- **How to interpret the evidence:** REA inspected shipped artifacts offline. ADB supplied the artifacts, resolver results and post-boot observations. A method body shows what the software can request; a post-boot snapshot shows state at the time of collection. Neither alone proves the order of events at boot or the physical response to a request. No activity was started and no reboot was performed. This is not a raw flash dump or a review of every executable.

## Two HOME decisions

1. **System to dispatcher (REA manifest + ADB resolver).** `com.newlink.wtprovision/.MainActivity` declares `MAIN` with `HOME`, `SETUP_WIZARD`, `MONKEY` and `DEFAULT` in one filter (priority 29). All categories in the incoming intent must match. `MAIN + HOME` returned WTProvision, RGTPLauncher, Nova, Projectivy and FallbackHome. Adding `SETUP_WIZARD` left only WTProvision; priority did not distinguish competing matches in that query.
2. **Dispatcher to launcher (REA method bodies).** On the normal HOME path `MainActivity.doSelectSourceId(-1)` calls `startActivity` with an explicit `ComponentName(home_pkg, home_activity)`. If the pair is missing, `getLauncherHomeActivity()` queries `MAIN + HOME` without `SETUP_WIZARD`, skips package names containing `wtprovision` or `com.android.tv.settings`, and takes the first remaining result. The stock launcher is a possible target, not a hard-coded destination. Factory video and source 10010 have separate branches; neither proves a HOME launch.
3. **Inside the stock launcher (REA method body).** If the pair names `com.newlink.hisilauncher/.WizardAciticity` (spelling in the APK), its `onCreate` reads `zysys.rgtp.launcher`. Values 1, 2 and 3 select `MainActivityNew`, `MainActivitySecond` and `MainActivityThird`; the default selects `MainActivity`. It starts the selected activity and finishes itself.

Within the stock launcher package, `WizardAciticity` is the HOME entry. Its filter also accepts the vendor action `android.zhiying.action.LAUNCHER`. The four destination screens each declare `MAIN` and `DEFAULT` but not `HOME`; `BaseActivity` has no filter. The APK requests `RECEIVE_BOOT_COMPLETED` but declares no broadcast receiver in its manifest. That permission is not evidence that a boot broadcast opened the launcher.

WTProvision and hisilauncher processes were present after boot. The sampled 4000 log entries did not identify a HOME handoff. Neither process presence nor resolver order establishes the pair used at the last boot. When interpreting a future trace, WTProvision's `onResume: package/activity` message reports the pair that `getLauncherHomeActivity()` just read from preferences. It is not an Android lifecycle notification. The actual `MainActivity.onResume()` calls its superclass and refreshes `isAppFirst` from the wizard property; it does not launch HOME. The log line alone proves neither delivery to the target nor that its screen appeared.

The dispatcher's cache is distinct from Android's preferred HOME activity. `getLauncherHomeActivity()` passes `home_pkg` and `home_activity` to `setWTProvision_sp()` in two separate calls. Each opens a `SharedPreferences` editor for the app, writes one string and calls `commit()` without checking its boolean result. Before reading either key back, the method checks its two in-memory fields. If either is null, it calls `getLauncherHomeActivity()` again immediately. The method has no retry delay or attempt limit. If the query keeps returning no eligible HOME and a field remains null, it repeats the query recursively rather than opening a chooser. This path was not observed at boot. This establishes where the dispatcher stores its choice, not the contents of the cache on the last boot. No preference was read from or written to the device for this check.

A second retry occurs after HOME selection. In `doSelectSourceId(-1)`, one `try` block covers constructing the explicit component, calling `startActivity()` and, on first run, writing the wizard property. Its exception handler calls `doSelectSourceId(-1)` without clearing the selected pair. If both fields remain non-null and factory-video mode is off, the retry uses the same component rather than querying for another HOME. The handler's “app not installed” log is not a diagnosis: even the property write after `startActivity()` returns can reach it. No such exception was observed in the sampled boot evidence.

Source 10010 with a nonempty `appSource` uses the configured package, not the cached HOME component. `startActivityPackages(String)` asks PackageManager for that package's launch intent, sets `NEW_TASK`, and calls `startActivity()`. It does not check for a null intent before setting the flag. On an exception it calls itself with the current `appSource` field rather than querying HOME or scheduling the source timer. `startActivityByPackage` is the log label, not the method name. This identifies a possible dispatch path, not the package opened at boot.

The source-switch timer is not a HOME launch delay. `doSelectSourceId()` returns from the factory-video and HOME branches before reaching `sendSourceMessageDelayed()`. In the remaining branch (except source 10010 with a nonempty app target), the helper clears pending callbacks and messages on `mHandler`, then posts one message with `what = this.sourceId`. It reads the delay in milliseconds from `persist.start_source_delay`. A parsed value of zero selects 5000 ms if the manufacturer string contains `MediaTek`, or 2500 ms otherwise. These are scheduling defaults, not a measured time to a picture or a launcher screen.

REA also identifies the timer's recipient: `MainActivity.MyHandler.handleMessage(Message)` reads a weak reference to the activity. If the reference still resolves, the handler calls `doSelectItemLogic(message.what)`; otherwise it skips that call. `MainActivity.onPause()` and `onStop()` only log and call their superclass; neither explicitly cancels the timer. `onDestroy()` calls `mHandler.removeCallbacksAndMessages(null)`, removing pending work on that handler, not undoing a source request already dispatched.

When the manufacturer string does not contain `MediaTek`, `doSelectItemLogic(id)` calls `selectHSSource(id, intent)` before starting the activity. REA shows three targets in priority order:

1. If `persist.display.720p` is false (default: true), PackageManager finds `com.newlink.nlsource`, and `id != 0`, the intent explicitly targets `com.newlink.nlsource/.MainActivity` with integer extra `SourceName = id`. The package lookup does not check for an input signal.
2. Otherwise, a nonempty `persist.newlink.wakeup_source` selects `ACTION_VIEW` with URI `yktv://source/mainpage?sourceid=` plus the property value, not the queued ID.
3. Otherwise the explicit target is `com.hisilicon.tvui/.MainActivity` with `SourceName = id`.

The caller catches exceptions from the final launch and its first-run/finish bookkeeping and queues another delayed message. A retry is therefore not proof of a missing player. No activity was launched to test these branches.

### Setup completion is separate from HOME launch

On the default first-setup branch in `MainActivity.onCreate`, WTProvision calls `setProvision()` before `doSelectSourceId(-1)`. REA shows that the helper requests three settings writes: `device_provisioned` in Global and the user and TV setup-complete flags in Secure, all set to 1. It then sets `persist.init.enable` to `false` and `persist.sys.country` to `cn`. It does not wait for a launcher result. A setup-complete flag therefore cannot establish that the selected HOME activity started or displayed a frame. Other wizard branches can take a different path; no settings were changed to test this sequence.

The optional Screeneo EasySetup wizard has two distinct call paths in `MainActivity.onCreate`. With `vendor.newlink.other.wizard.type=1` in the first-setup branch, the activity writes the three setup flags, then calls `startOtherWizard` with an explicit EasySetup intent. The helper calls `startActivity`, then `setProvision`, sleeps 10 ms and calls `finish`. The caller has no immediate `return` after the helper. By contrast, the `zysys.philips.wizard` branch, if reached, calls `setProvision` and `doSelectSourceId(-1)` before requesting EasySetup. A request to display the external wizard is therefore not an alternative HOME resolver result. Neither path was exercised, and the installed EasySetup component and effective properties were not verified.

## Vendor packages and boot

**Packaged assets.** Across the 19 checksum-matched APKs, five files sit under `assets/` in three packages. HiTvPlayer and HiTvSetting each contain English and Chinese ISO 639 properties files. Corresponding filenames match across the two apps, but their contents differ by SHA-256. WTProvision contains `assets/live.json` (466,910 bytes), a bundled TV channel catalogue. Its `data` array contains 2,073 records with distinct `id` values but only 1,685 distinct `title` values. Every row has `epg_id`, `epgname`, `hd`, `id`, `num`, `province`, `status` and `title`; 11 rows also have `types`. These are catalogue entries, not measured tuner channels or verified playable streams. This inventory excludes Android resources under `res/` and does not establish which assets the apps read at runtime.

**Voice service lifecycle (REA).** WTProvision's `TVService.onCreate()` constructs `AliTVASRManager` and calls `init(this, false)`. Each `onStartCommand()` calls `initData()` and returns `1` (`START_STICKY`). `initData()` starts a thread to register the command listener and separately requests result mode `2` on the calling thread. The service's `onDestroy()` only calls its superclass. These methods show how the callback is registered, not whether the service ran or a microphone captured audio.

**Channel catalogue consumer (REA).** In WTProvision's `TVService$1.onNLUResult()`, a voice-command callback checks a result flag and the saved `statusInfo` text before opening `TVService.FILE_PATH` through `readAssertsFile()`. The DEX field value is `live.json`; the helper calls `AssetManager.open(String)`. The callback parses `Product.data` with Gson. For channel names it passes the list to `startTVChannelName()`; for supported numeric phrases it compares the requested number with catalogue `num` and passes a matching number and a `ChangeChannel` intent targeting `com.cloudmedia.videoplayer` to `whetherInstallAPK()`. This identifies a reader, not a successful voice command or channel change. Separately, `InstallLiveApkActivity.onCreate()` requests a download and its success callback passes the local path to `installApk()`. Neither operation was run.

**What the voice callback acknowledges (REA).** At `ASR_STATUS_RECOGNIZE_END`, `onASRStatusUpdated()` saves `String.valueOf(bundle)` as `statusInfo` if that string is nonempty. `onNLUResult()` reads this text and calls `extracted()` after its channel-selection branches. Even a supported numeric request with no matching catalogue number can reach that call without requesting a channel change. `extracted()` marks the command handled and builds a `method: success` reply without consulting the player. This is a local acknowledgement, not evidence that the channel changed.

**Channel selection by name (REA).** `TVService.changeChannelName()` checks built-in aliases first (`cctv16` maps to `CCTV-5+体育赛事`), then looks for an exact catalogue title. A match sets `channel_name` and calls `startTVLive()`; an unmatched title falls through without that call. If the player package passes the installation check, `startTVLive()` adds the caller package as `from` and calls `startService(intent)`. Otherwise it requests `InstallLiveApkActivity` in a new task. These are dispatch requests, not evidence of service delivery or playback.

**Bytecode coverage.** A ZIP inventory of the 19 digest-matched, unmodified vendor APKs found one root `classes.dex` with standard DEX magic in each of seven: HBCastNew, HiVideoPlayer, IjkPlayer, NLSourcePlayer, NewLinkService, RGTPLauncher and ZYCustomer. The other 12 had no standard root `classes*.dex` entry. Their manifest declarations remain inspectable, but an unresolved method in one of those APKs is not evidence that Android lacks its implementation. WTProvision is the verified counterexample: its method bodies were recovered separately from stock VDEX. Analysis APKs with recovered bytecode are excluded from these counts.

In the live user 0 snapshot, PackageManager listed 78 distinct packages. Its system filter returned 76 and its non-system filter returned two; the sets were disjoint and their union matched the unfiltered list. Exactly 19 of the 78 names had the Newlink or HiSilicon prefixes used for the REA inventory below. Package counts include framework and service packages, not just launchable apps. The non-system package names were not published. The namespace filter describes audit coverage, not authorship of every package in the image.

Among activity and activity-alias rows in the 19-package inventory, five distinct packages declare the conventional `LAUNCHER` category, two declare `HOME`, and one declares `LEANBACK_LAUNCHER` (Miracast's `WelcomeActivity`). These counts use exact category names and can overlap. They describe declarations, not how many tiles the vendor home screen displays. HiVideoPlayer is a concrete example: its `VideoActivity` puts `MAIN` and `LAUNCHER` in a filter that also requires a `file:` or `content:` URI and a `video/*` MIME type. A conventional launcher query without data does not match that filter, even though the activity contributes to the category count.

Grouping the active APK paths of those 76 system packages gave 42 in `/system/app`, 27 in `/system/priv-app`, one in `/system/framework`, four in `/vendor/overlay`, one in `/vendor/app` and one in `/data/app`. The last package's record carried both `SYSTEM` and `UPDATED_SYSTEM_APP`: Android still classifies it as system software while using its updated copy from writable storage. For firmware comparisons, distinguish the APK currently in use from the copy shipped in the read-only image. Directory counts alone do not establish effective permission grants or which overlays are active.

For user 0, OverlayManager matched all four vendor overlay APK paths. The three display-cutout emulation overlays (corner, double and tall) target `android` and each had `STATE_DISABLED`. The dark theme overlay targets `com.android.systemui` and had `STATE_MISSING_TARGET`. All four had `mIsEnabled: false`. None of these four overlays was applying resources in that snapshot. The dark theme state describes target resolution by OverlayManager, not how the launcher draws its own theme.

The [component inventory](vendor-manifests-2026-11-27.csv) contains 152 REA declaration rows for the 19 installed packages in the `com.newlink.*` and `com.hisilicon.*` namespaces. Eighteen manifests had complete declaration coverage; HiTvService returned four declarations with partial coverage. An empty `exported` field means no explicit value was recorded, not `false`. The 152 rows break down into 104 activities, one activity alias, 33 services, nine receivers and five providers. HiTvService contributes three service rows and one provider row. A separate REA read of its entire decoded manifest confirms those four components. The partial label belongs to the structured inventory, not the decoded XML text. These counts describe the saved declarations, not how many apps appear in the launcher or how many services were running.

HiTvService declares all three vendor Java libraries as required: `com.hisilicon.android`, `com.hisilicon.dtv` and `com.hisilicon.android.tvapi`. Its `TvService` requires `COMMON_PERMISSION`, while `SettingService` and `BookTaskService` are not exported. The exported `TvServiceProvider` has separate read and write permissions (`com.hisilicon.tv.service.read` and `.write` under the same prefix). All three named permissions are declared with `signatureOrSystem`. The manifest establishes these requirements, not effective grants to any running client.

NewLinkService and HiTvSetting declare `BOOT_COMPLETED` receivers. The latter declares `com.hisilicon.permission.COMMON_PERMISSION`. The HDMI, YPbPr, CVBS and VGA TV input services declare `BIND_TV_INPUT`. ADB showed zygote, system_server, surfaceflinger, both HOME packages, com.newlink.service, com.hisilicon.tv.service and com.hisilicon.rmservice running; bootanim was stopped. This snapshot does not order their startup.

REA decoded `NewLinkService`'s `BootCompleteReceiver.onReceive(Context, Intent)`. It checks the action for exact equality with `android.intent.action.BOOT_COMPLETED`. If `ro.zhiying.model` does not contain the case-sensitive substring `3S`, it first requests `com.newlink.hisetting.message.MessageService` in the `com.newlink.hisetting` package. It then requests its own `com.newlink.service.service.BootService`, which its manifest declares. On the `3S` branch it skips the settings request and goes straight to `BootService`. The first request names a component that the inspected settings APK does not declare. REA returned both service entries from the complete ZYCustomer manifest: `com.newlink.hisetting.MyService` and `com.newlink.hisetting.ProjectionService`. An explicit request for `MessageService` does not select either by similarity. The receiver ignores the first `startService` return value before requesting `BootService`; it does not catch an exception from that call. These are static findings, not a recorded failure or proof that either service started on the observed boot.

`BootService.onStartCommand()` schedules a callback after 60 seconds, measured from the service start request, not power-on. The callback checks activation when `getAuthenticate()` returns 0 and either the model contains `3S` (default here: `3S`) or the manufacturer equals `MediaTek`. Within that branch it requests `ActivationActivity` if `START_TIME == 0` and Android reports no available active network. Otherwise it resets `START_TIME` to zero and schedules another `BootService` request five minutes later using elapsed realtime. On normal return the callback calls `startMyService()` outside the activation branch; REA resolves that helper to an explicit request for `MyServices`. No callback, activity launch, alarm delivery or network traffic was observed in this offline inspection.

### Data prepared by the boot reporting service (REA)

Starting `MyServices` does not itself prove a report was sent. `onCreate()` reads the MAC, customer name, project ID, system version and system date through vendor helpers. `onHandleIntent()` checks connectivity and authentication state. For state 0 or 2 it attempts a plain HTTP IP-location lookup, then queues an activation report. A separate check for state 1 performs the lookup and queues two POSTs (verification and usage time) with the same JSON body. That path explicitly sets usage time to **zero**; the field is not a measurement of time spent using the projector. The city field comes from the filtered lookup response, not GPS. A lookup exception skips the remaining requests in that branch. See the [vendor telemetry guide](VENDOR_TELEMETRY.md) for the broader system context. No endpoint was contacted, payload captured or device identifier collected for this trace.

## Build and storage (ADB)

The framework reports security patch level `2019-11-05` (`ro.build.version.security_patch`). This is the build's declared Android patch level, not its build date or a verification of individual backports. A separate query for `ro.vendor.build.security_patch` returned an empty value, so that property does not establish the vendor patch level. Likewise `ro.vndk.version=28` identifies a native interface version, not proof of Treble support: this build explicitly sets `ro.treble.enabled=false`.

Android 9 (API 28), `PPR1.180610.011`, incremental `eng.hudson.20220706.192233`, `userdebug/dev-keys`. The root and vendor filesystems were mounted read-only as ext4. By-name links mapped recovery to p5, logo to p8, boot to p9, misc to p15, system to p20, vendor to p21, cache to p24 and userdata to p25. Reported filesystem capacities and use: `/` 1.7 G (88%), `/vendor` 291 M (16%), `/data` 4.4 G (38%), `/cache` 93 M (1%). These are filesystem measurements, not raw partition sizes.

Android's volume daemon (`vold`) was running, and StorageManager reported both `private` and `emulated` volumes mounted. In the ADB shell mount namespace the userdata block device backs ext4 at `/data`; `sdcardfs` exposes `/data/media` at `/storage/emulated`. The `/sdcard` alias points to `/storage/self/primary`, which in turn points to `/mnt/user/0/primary`. The emulated shared-storage view therefore consumes space on userdata, not a second disk: do not add its reported capacity to `/data`. This describes the active internal storage arrangement, not support for removable media. No user files were enumerated.

The board init file invokes `mount_all /vendor/etc/fstab.${ro.hardware}`. In the resolved `fstab.bigfish`, the `/data` entry requests `wait,check,quota,reservedsize=104857600` (100 MiB reserved); `/cache` requests `wait`. The live mount table confirms both are writable ext4 using `data=ordered`. The 100 MiB figure is a configuration request, not a measurement of current free space. Mount flags alone do not establish that a filesystem check ran at the last boot or that a quota was enforced for a particular app.

## Board identity and Android startup configuration

The running device tree reports model `Hi3751` and compatible `hisilicon,hi3751`; `/proc/cpuinfo` reports hardware `hi3751`. Android uses the board name `bigfish` for `ro.board.platform`, `ro.hardware` and `ro.boot.hardware`. These are complementary identifiers, not different devices. The kernel showed CPUs `0-3` online, each reporting implementer `0x41` and part `0xd03` (Arm Cortex-A53). That core identity does not imply a 64-bit Android build: the running kernel reports `armv7l` and Android selects `zygote32`. These software observations do not identify a finer chip stepping or package marking.

The main MMC user block device reports type `MMC`, product name `UEM`, and 14,942,208 Linux 512-byte sectors: 7,650,410,496 bytes (7.125 GiB). This is the capacity exposed by `mmcblk0`, not free space, the size of userdata, or a physical NAND inventory.

On-device init configuration connects these identifiers to startup. `/init.rc` imports `/init.${ro.hardware}.rc`, `/vendor/etc/init/hw/init.${ro.hardware}.rc` and `/init.${ro.zygote}.rc`. Both resolved `bigfish` files exist. The resolved `/init.zygote32.rc` declares `zygote` as `/system/bin/app_process -Xzygote /system/bin --zygote --start-system-server`. In the post-boot snapshot init reported zygote running and Android reported `sys.boot_completed=1`. This identifies the configured path into the Android framework, not a replay of every init action or proof that every service was ready.

## Application compatibility and vendor Java APIs

REA decoded the stock launcher's version as `22.02.13` (code `220212`). Its manifest sets minimum API 16 and target API 29. The projector's API 28 meets the minimum; the higher target is not evidence that the projector runs Android 10. The launcher also declares Bluetooth LE as required and lists the GPS feature. These describe the APK's hardware expectations, not a GPS receiver detected on the board.

The stock app ABI list is `armeabi-v7a,armeabi`, the 64-bit list is empty, and `/system/bin/app_process` resolves to `app_process32`. An app that requires an `arm64-v8a`-only native library has no matching stock app ABI. This restriction concerns native code, not ordinary DEX bytecode; an ABI match alone does not guarantee installability or correct behavior.

Offline ZIP inspection matched all 19 stock APKs to the SHA-256 digests in the manifest inventory. Four contain conventional `lib/<abi>/*.so` entries and all four include `armeabi-v7a`. Cast ships only that ABI (16 entries); IjkPlayer includes five ABIs, and WTProvision and HiSetting each include four. The latter three include `arm64-v8a`, despite stock Android exposing no 64-bit app ABI. A separate header check found 39 little-endian ELF files. Their bitness and machine family match their directory labels (the ARM machine field alone does not distinguish `armeabi` from `armeabi-v7a`). Of these, 38 have type `ET_DYN`; Cast's `lib/armeabi-v7a/libicast_arm.so` has type `ET_EXEC` despite its `.so` suffix. All six program headers in that executable were decoded. They include two `PT_LOAD` segments and neither `PT_INTERP` nor `PT_DYNAMIC`: the executable does not name an ELF interpreter for startup. That does not establish whether Android launched it or what resources it would need at runtime. The other 15 APKs lack entries at that path; they can still use native libraries supplied by the system or by another component.

PackageManager lists three HiSilicon Java libraries. The stock XML under `/system/etc/permissions` maps `com.hisilicon.android` to `HitvManager.jar`, `com.hisilicon.android.tvapi` to `HitvShare.jar`, and `com.hisilicon.dtv` to `HiDtvShare.jar`, all under `/system/framework`. These library names are framework dependencies that vendor apps can request, not Android application package names. Registration alone does not prove which app uses a given API.

For a concrete consumer, the live package record for `com.newlink.wtprovision` lists `com.hisilicon.android.tvapi` under `usesOptionalLibraries` and `/system/framework/HitvShare.jar` under `usesLibraryFiles`. Stock Android thus resolves the optional library for the provisioning app. This does not prove that any one of its methods called the API during boot or that all features work without it.

REA's complete decoded manifest for the stock external TV input APK shows a different contract: minimum and target API 28, Leanback and Live TV required, touchscreen optional. Its HDMI, YPbPr, CVBS and VGA services advertise the Android `TvInputService` action. The requirements describe the software environment expected by this APK, not a physical inventory of inputs.

HiRMService differs from WTProvision: its manifest lists `com.hisilicon.android` and `com.hisilicon.dtv` without marking either library optional. The application is `persistent` and `directBootAware`. Its service advertises the Android accessibility service action, requires `BIND_ACCESSIBILITY_SERVICE` of the caller, and points Android to `@xml/filter_event_service`. These declarations identify dependencies and a binding interface. Seeing the process in the ADB snapshot does not establish that Android bound the accessibility service, that it received remote-control keys, or that it ran before user unlock.

The compiled `filter_event_service` XML in the same SHA-256-matched APK declares `canRetrieveWindowContent=true`, event mask `0x400000`, feedback mask `0x10` and flags `0x40`. These are static settings, not a record of reading a window. The offline binary XML decoder was checked against the binding permission in the manifest decoded by REA. No screen content was collected.

The APK also ships a layout named `activity_black_screen`. Its compiled XML contains one `RelativeLayout` element and no child views. Both dimensions encode `-1` (`match_parent`); the background is a framework resource reference (`0x0106000c`), not an inline color. Matching the parent does not establish that the parent fills the display. Despite the filename, REA's complete manifest inventory lists one service and no activity. The resource alone does not identify what inflates it, whether an overlay appeared or whether the projector switched off its light source.

## Board services and radio drivers

The root `bigfish` init configuration requests `bootvideo` at `init`. At `post-fs` it requests `hwsysmanager-1-0`, `vendor.hiavplayer`, `hwandroidmediahal-2-0`, `hwtvmw-1-0` and `hidl_memory`. All five reported `running` after boot. `bootvideo` reported `stopped`; that state does not show whether a boot video played. The vendor configuration mounts the board fstab at `fs` and requests `vendor.ir_user` and `vendor.virtualkeypad` at `boot`. Both reported `running`. This ties two input services to board startup, not a particular remote button to either service.

The vendor boot action lists several alternative Bluetooth modules; the file alone does not identify the fitted radio. In the running kernel, `wlan0` and `p2p0` both point to the same USB parent, with vendor/product ID `a69c:8801`. Two interfaces on that device bind to `aic_btusb` and the third binds to `aic8800_fdrv`. This identifies the stock composite radio's driver pair without scanning or pairing. It does not identify the exact silicon revision or verify radio performance. `eth0`, by contrast, points to the `hieth` platform driver.

Above the kernel driver, PackageManager advertises Bluetooth and Bluetooth LE. The Android Bluetooth manager reported the adapter enabled and `ON` in this snapshot. The vendor A2DP audio policy declares output routes for Bluetooth headphones and speakers, plus an input route. These are logical Android audio paths, not evidence of a connected accessory, an active stream, or a working end-to-end receiver mode. No discovery or pairing was requested.

In WTProvision's Bluetooth setup screen, `BluetoothActivity.onCreate()` registers for device discovery, adapter state, bond state and ACL connection broadcasts. `getBluetoothProfile()` requests profile 4 if the adapter exists and the activity has no cached proxy. ## Source player: from a vendor choice to an Android TV input

NLSourcePlayer's `MainActivity` declares the `android.newlink.source` action. REA decoded three steps: `onCreate()` enumerates `TvInputManager.getTvInputList()` and remembers IDs containing `cvbs` or `vga` (case-insensitive); `initData()` maps the integer `SourceName` to an ID; `onResume()` requests `TvView.tune()` with that ID and its passthrough channel URI. The player's `no_signal_tip` is a delayed Android UI indicator, not a cable detector. `onVideoUnavailable()` replaces any pending message `1` with a new one due in 1,500 ms, regardless of the reported reason. The handler for message `1` calls `tipLayout.setVisibility(0)` and returns `false`; it does not open a dialog. A separate no-signal dialog key listener calls `finish()` on BACK key-down, but that is not part of the delayed tip path. Both `onVideoAvailable()` and `onContentAllowed()` cancel the pending message and hide the tip immediately. The stock manifest sets `MainActivity` to `singleInstance`. On the next `onResume()`, `initData()` reads that saved intent before the player requests the input. Conversely, `onStop()` resets the `TvView` and clears the handler queue, including any pending no-signal warning. This is a reset of the Android view, not evidence that the physical input was powered down.

If `MainActivity.onKeyDown()` receives DPAD_LEFT or DPAD_RIGHT (21/22), it consumes the event and requests the current media volume (stream 3) minus or plus one step, with the volume UI flag. MENU (82) instead requests the implicit `com.hisilicon.android.intent.action.tvsetting` activity and then delegates to the superclass if the request returns. With `6dsensor`, autofocus enabled and `mStartFocus` set, the accelerometer callback replaces a pending `autoFocusRunnable` with one delayed by 500 ms. These are separate branches: the accelerometer callback does not itself demonstrate an image correction. The property values, callback delivery and optical result were not measured in this trace.

Despite its name, `autoKeystone_3d_Runnable` (`TempService$5.run`) does not directly set image geometry. It compares the recorded pitch and roll ranges separately. If either exceeds 5 raw units (exactly 5 does not qualify), 3D autofocus is enabled, and the current activity is not `com.zhiying.autofocus.AutoFocus2Activity`, it queues `autoFocusRunnable` after 10 ms with status 0. That runnable (`TempService$4.run`) sets `sys.newlink.auto` to `1` and requests an activity with the implicit action `com.zhiying.AUTO_FOCUS`, `FLAG_ACTIVITY_NEW_TASK` and the `auto_keystone_startstatus` extra. On `ActivityNotFoundException` it schedules itself again after 1000 ms. The activity name used in the guard is not an explicit intent target. This offline trace establishes the handoff request, not which activity resolves it or whether the projected image changes.

The saved REA manifest inventory has no activity or activity-alias row declaring the exact action `com.zhiying.AUTO_FOCUS`. The same exact-action lookup found `com.newlink.cast_qlto1` on `MainCastQLTo1Activity` as a control. This inventory covers Newlink and HiSilicon packages, not Zhiying packages. HiTvService's complete decoded manifest declares neither activities nor aliases. The earlier string scan of Zhiying Settings mentions `com.zhiying.autofocus`, but that is not an intent filter. The installed resolver target remains unknown: the read-only ADB connection timed out before a PackageManager lookup could run.

REA also decoded `TempService.onDestroy()`: it calls `super.onDestroy()` and unregisters `mBtReceiver`. This method does not explicitly cancel the queued autofocus retry or unregister the vendor sensor listeners. That does not establish that a retry runs after teardown: neither the service lifecycle nor callback delivery was observed.

### Thermal notifications at service creation

REA places thermal registration in `TempService.onCreate()`, before `startSensorsListener()`. Its `startTemp()` helper sets `zysys.temp.enable` to `true`, creates a `Handler`, and passes a callback to `TvCustomSetting.setThermalListener`. Although a log string in the helper mentions `onStartCommand`, the service's `onStartCommand` override only logs and delegates to its superclass. The camera checks inside `startSensorsListener()` therefore do not gate this thermal registration. This is a code path, not a temperature reading, fan-speed measurement or observation that the service ran at boot.

On the HiSilicon path, `setThermalListener` subscribes to `NL_TV_EVT_EX_CUS_THERMAL` through `setCusExListener`. The helper unregisters its previous delegate for that event before registering a replacement. Passing null removes the existing delegate without replacing it. This changes which notifications the app receives; it does not change the thermal policy or turn off a sensor.

The fan query is distinct from the thermal listener. WTProvision's `HiTvCustomSetting.isFanEnable(int)` forwards its argument to `CusEx`. In HitvShare, `CusExImpl.isFanEnable(int)` returns true only if `CMD_ID_EX_CUS_GETFANENABLE` returns exactly 1. The caller receives a boolean, not an RPM reading; false cannot distinguish zero from another returned integer. Neither the physical fan count nor rotation was measured.

WTProvision also exposes `HiTvCustomSetting.GetThermalPolicy()`. Unlike the fan query, this getter takes no index and returns an integer unchanged: HitvShare's `CusExImpl.GetThermalPolicy()` forwards `CMD_ID_EX_CUS_GETTHERMALPOLICY` to `HitvManager.excuteCommandGet`. Neither wrapper decodes policy values or reads a temperature. The active policy and its thresholds remain unknown.

HitvShare's `OnCusExListener.notifyThermalMessage` selects the callback by event type, not by comparing a temperature with a threshold. It forwards a temperature value only to the informational callback. Fan events go to a separate method, `notifyFanMessage`, whose base implementation is empty. This does not rule out a subclass handling fan events elsewhere.

REA decoded four thermal callbacks in `TempService$7`. Temperature reports and LSADC errors only log their arguments in these methods. An overheat warning logs the message and calls `QUtils.showTempDialog` unless the dialog flag is already set. A thermistor error has two separate, default-on checks: one opens `ShutdownTipActivity`; the other schedules a task after 5 seconds. That task clears the thermal listener and requests Android shutdown with reason `thermal`. The delay starts at error handling, not at a measured temperature crossing. No event was induced, and neither effective settings nor a completed shutdown were observed.

`QUtils.showTempDialog(Context)` displays an alert with an OK button whose click handler is empty. When the customer property contains `dangbei`, the text warns of impending automatic shutdown; otherwise the helper uses the `temp_dialog_msg` resource. Neither the helper nor its button requests shutdown. The warning text is not evidence that a shutdown timer started, or that this unit displayed that variant.

### Bluetooth profile selection after a link connects

WTProvision has a separate vendor service request. `MainActivity.startBTService()` calls `Context.startService()` with the explicit component `com.newlink.bluetooth/.BTService`. It ignores the returned component; if the call throws an exception, the helper calls itself immediately. This method does not enable the Android Bluetooth adapter or verify a connection. A second method, `MainActivity.lambda$onCreate$0()`, requests the same component but only logs an exception and returns. The recursive retry belongs to the first helper, not to every request for that service. In contrast, `MainActivity.startBluetooth()` requests WTProvision's own `BluetoothActivity`, not the vendor service. `MainActivity.onCreate()` schedules the vendor-service callback on `mHandler` with a 12,000 ms delay when `isAppFirst` is true and `sys.newlink.bt_ac695n_enable` is `1` (default `0`). The screen follows a different branch: with both `isAppFirst` and `systemInitFirstTime` true, `persist.newlink.blhdmi` not equal to `2`, and `zysys.match_irui_jinju` equal to `1`, the activity requests `BluetoothActivity` directly, finishes and returns on success. A launch exception takes the `startBluetooth()` retry path. The two sets of conditions can overlap; neither the scheduled delay nor the screen request establishes what ran at the observed boot.

In WTProvision, `TempService` requests Bluetooth profile proxies 1, 2 and 4 with one listener. REA shows that `TempService$9.onServiceConnected` ignores the profile ID and overwrites a single `mProfile` field. On `ACL_CONNECTED`, `TempService$8.onReceive` stores the device from the broadcast. If a proxy is present, it queues a delayed call to `connectHid`. The queued task reads both fields when it runs, not when it is queued.

Despite its name, `connectHid` does not select the HID profile. It looks up `connect(BluetoothDevice)` on the supplied proxy by reflection, ignores the return value and catches exceptions. This explains a possible profile connection attempt after a Bluetooth link comes up; it does not identify the remote, prove pairing or establish which profile connected. No Bluetooth device was connected for this analysis.

The profile listener's `onServiceDisconnected(int)` is empty: that callback does not clear the stored proxy. This is a profile-service notification, not evidence that a physical remote disconnected.

### Optional voice services

WTProvision has separate switches for AliTV and Qcode. `MainActivity.onCreate()` requests its own `TVService` through `startService()` when `isAppFirst` is true and the boolean `vendor.newlink.ali_yuyin` is true (default false). This branch does not test the Qcode property. The AliTV command listener is registered from the started-service path described above, not supplied to clients by `onBind()`. These conditions identify which software can receive voice results, not which microphone or remote is present.

REA shows a separate branch in `TempService.onCreate()`: when `vendor.newlink.shijiu_yuyin` reads as `1` (default `0`), it schedules a task to start `com.qcode.tvvoicehelp.services.AIVoiceService` in package `com.qcode.tvvoicehelp`. The task sets the explicit component and the action `com.qcode.acion.voicehelp` (spelling in firmware). If `startService` throws an exception, it schedules another attempt after 500 ms. This identifies the intended Android service, not the effective property value, an installed handler, microphone use or a successful launch on this unit.

REA also identifies the caller upstream of `TempService`: `WTProvision.MainActivity.onCreate` explicitly requests it when `isAppFirst` is true. Later in the same method, if `isAppFirst`, `systemInitFirstTime` and the voice property are all set, the activity requests the same Qcode service directly. Unlike the delayed task, the direct call catches an exception without retrying. `initSharedPreference()` reads `systemInitFirstTime` from `persist.init.enable` (default true); the field is not a boot counter. These are two possible requests to the same component, not evidence of two service instances or two launches during boot.

## Android audio policy and input endpoints

The vendor audio policy includes a primary HAL 2.0 module. It declares `Speaker` as the default output and routes `primary output` (48 kHz, stereo, 16-bit PCM) to that sink. The live `media.audio_policy` dump also lists the primary module, `Sink: Speaker` and `AUDIO_DEVICE_OUT_SPEAKER`. This confirms Android's logical route, not the connection from the HAL to ALSA or the amplifier. Both `audio.primary.bigfish.so` and `audio.primary.default.so` are present under `/vendor/lib/hw`; filenames do not identify which one was loaded. No playback or capture test was performed.

At the app layer, HiMusic advertises `TransitActivity` as a handler for `VIEW` requests with `file:` or `content:` URIs and MIME type `audio/*`, `application/ogg`, `application/x-ogg` or `application/itunes`. For `VIEW` intents that also specify `BROWSABLE`, the local-file filter does not match. Two other filters accept the same MIME types: one for `http:` and one for `content://media/...` with priority `-1`. The `media` authority restriction belongs to that last filter, not to ordinary `content:` requests without `BROWSABLE`. The manifest also declares `MediaPlaybackService`; the playback screen itself (`MediaPlaybackActivity`) is not exported. These REA observations identify the resolver entry point, not the default handler or codecs that successfully play on the unit.

The optional WTProvision mute indicator reports Android media volume, not amplifier state. REA shows that `MainActivity.onCreate()` requests `MyMuteListenerService` when `isAppFirst` is true and `zysys.wtp.mute.vis` equals `1` (default `0`). On `android.media.STREAM_MUTE_CHANGED_ACTION`, its receiver reads `AudioManager.getStreamVolume(3)` rather than the stream ID in the broadcast. At zero it adds or updates an image view; above zero it removes the view if attached. The receiver changes the indicator, not the volume. Its code does not establish whether the indicator appeared on this unit or whether the speaker was silent.

The icon can also appear without a new mute event. `MyMuteListenerService.onStartCommand` checks media volume on a non-null start intent and requests the icon if volume is already zero. At nonzero volume it returns without removing an existing icon, unlike the broadcast receiver. A null intent skips the check. The receiver filter registered in `onCreate` subscribes to stream mute changes, not ordinary volume changes. Seeing the icon would therefore not, by itself, date a mute keypress. `onDestroy()` calls its superclass and unregisters the mute receiver; it does not explicitly remove the icon. The icon's lifetime after service teardown was not observed.

The four input event nodes in this snapshot were `Hi keyboard`, `Hi mouse`, `qwerty` and `Hi Keypad`. All resolve under `/sys/devices/virtual/input`, not to a physical receiver bus. Android can map the virtual key devices to layouts, but these sysfs paths alone do not identify the event producer. The vendor init configuration starts `android_ir_user` (not the similarly named `ir_user`) and `virtualkeypad`; both executables appeared in the post-boot process list. Offline REA ELF inspection of device-checksummed copies found that both depend on `libhi_msp.so`, but `android_ir_user` specifically imports `HI_UNF_IR_GetValueWithProtocol`, `HI_UNF_IR_GetSymbol`, and controls for key-up and repeat handling. A separate byte-string inspection found `/dev/vinput` in `android_ir_user` and `/dev/uinput` in `virtualkeypad`. This distinguishes the IR reader candidate from the second input service; the two path literals do not prove that either node was opened, that one service calls the other, or which virtual event node carries a particular button.

## Opening versus sharing a video

REA shows different entry points for the two stock video players. For an implicit `VIEW` request with a `content:` or `file:` URI and type `video/mp4`, HiVideoPlayer's `activity.TransitActivity` declares the action, `DEFAULT` category, schemes and `video/*` type together. In IjkPlayer's Newlink `activity.VideoActivity`, the `VIEW` filter has no data declaration; the separate `video/*` filter specifies `MAIN`, not `VIEW`. Android matches each filter separately, so neither of those filters matches that example. Sharing is different: IjkPlayer's `tv.danmaku.ijk.media.example.activities.VideoActivity` declares `SEND`, `DEFAULT` and `video/*` together. These manifest matches do not identify a user-selected default or demonstrate playback.

After Android selects HiVideoPlayer, `TransitActivity.onCreate()` forwards the URI and MIME type to an explicit `MediaFileListService` intent. If the URI path ends in `.ISO` after uppercasing, it substitutes `video/iso` without inspecting the file contents. It copies the `sortCount` integer (default `-1`), requests the service and finishes the activity. A missing incoming intent or a non-null URI with a null path returns before the service request. This handoff identifies where processing continues; it does not demonstrate that a disc image was mounted or decoded.

`MediaFileListService.onStartCommand()` checks the reported foreground activity before clearing the playlist. If its class name starts with `com.hisilicon.android.videoplayer.activity` and is not exactly `TransitActivity` in that package, the service returns without examining the new URI. The `stopSelf` text on that branch is a log message, not a call to stop the service. Without a match, the service clears or initializes the list, resets its position to zero and passes a non-null intent to `getCurPath()`. This distinguishes a request reaching the service from the service accepting it for processing.

For a resolved file path that passes the service's path checks and has an existing parent directory, `getCurPath()` calls `startVideoActivity()`. That helper starts a playlist worker for the parent directory, then explicitly requests `com.hisilicon.android.videoplayer.activity.VideoActivity` without waiting for that new worker to finish. The activity receives the original URI, a `MediaFileList` extra with the resolved path and filename, and MIME type `video/*` even when the service received `video/iso`. If the intent has no data URI, `getCurPath()` starts a list worker with a null directory instead of calling this helper. Neither path establishes that a decoder opened the media.

The playback screen and the player have separate start conditions. In the APK bytecode, `VideoActivity.access$1800` returns its `HisiVideoView` field. That view's `start()` calls `mediaPlayer.start()` only if the player exists and `mIsPrepared` is true; otherwise it sets `mStartWhenPrepared` and returns without starting playback. REA did not resolve `VideoActivity.onCreate()` in this lookup, so these observations do not establish when the screen first calls the view, which codec is selected, or whether a frame is displayed.

`HisiVideoView.openVideo()` requires both a URI and a display surface holder. When creating a new `MediaPlayer`, it clears the ready flag, installs the prepared listener, passes the URI string to `setDataSource()`, and binds the holder with `setDisplay()`. A missing subtitle surface is logged but does not skip `initVideoFormat()` or `prepareAsync()`. This identifies the handoff to Android's media framework, not the decoder or physical display path used for a particular film. For an existing player, `openVideoByMediaPlayerExit()` resets and reuses the same object. It clears the ready flag, resets the duration, buffering percentage and selected audio/subtitle track IDs, and assigns the new URI. Before `prepareAsync()` it selects a stereo strategy using the app's format and 3D adaptation settings. These calls are not evidence that the projector switched optical modes.

Playback controls can change pending requests before the player is ready. `HisiVideoView.pause()` clears `mStartWhenPrepared` even if there is no prepared player to pause. It calls `MediaPlayer.pause()` only when the player exists, is prepared and reports it is playing. `seekTo(int)` forwards the position immediately if the player exists and is prepared; otherwise it overwrites `mSeekWhenPrepared`. Two seeks before preparation therefore store the last position, not a queue. Assigning a URI discards that pending position: `setVideoURI(Uri)` stores the URI, clears `mStartWhenPrepared` and resets `mSeekWhenPrepared` to zero before calling `openVideo()`. It does this on every assignment, even for the same URI. The reset changes a field; it is not a `MediaPlayer.seekTo(0)` call or evidence of a frame on screen.

The time label is not a decoder-position readback. `VideoActivity$6.onProgressChanged()` formats the seek bar's supplied position for the label on both user and programmatic updates. Only a user update resets fast forward or rewind if active and passes the position to `HisiVideoView.seekTo(int)` (direct DEX call at code-unit offset 32). The callback does not wait for seek completion before updating the label.

The view also exposes two different time readings. Without a prepared player, `getCurrentPosition()` returns `0` without querying Android, while `getDuration()` sets and returns `-1`. Once prepared, the view asks `MediaPlayer` for the current position on every call but reuses a positive cached duration. A position of zero alone therefore cannot distinguish an unprepared player from one at the start of a film.

A controller reading the Android media session gets a different kind of position. The DEX instructions in `MediaSessionWrapper.<clinit>` build the `PLAYING`, `PAUSED` and `STOPPED` states once, each with position `0`. `setPlaybackState()` publishes those objects without asking `MediaPlayer` for its position. A zero in that session update is therefore not evidence that playback restarted or a seek landed at the beginning.

Unlike `pause()`, `HisiVideoView.destroyPlayer()` clears the view's surface-holder reference. If a media session wrapper exists, `setPlaybackState(false, false)` publishes `STOPPED` only if the Android media session is active. The subsequent `release()` calls `MediaSession.release()` whether or not that update was sent. Thus the session can be released without a final `STOPPED` update from this method. If a `MediaPlayer` exists, it resets and releases it, then clears the player reference. These are app-level cleanup calls, not evidence of when the hardware decoder stops or the projected frame disappears.

In HiGalleryL, REA found a `VIEW` / `DEFAULT` filter on the landscape activity `com.hisilicon.higallery.NetworkHiGallery`. Despite its name, it accepts `file:` and `content:` as well as `http:`. ## File manager entry points

In the stock Newlink file manager (6.0), `activity.SelectActivity`, not `activity.MainActivity`, declares `MAIN` with `LAUNCHER`. The USB screens `UsbCountActivity` and `USBAllActivity` declare `MAIN` with `DEFAULT`; those filters are not USB attachment notifications. The manifest also declares an AndroidX FileProvider that can grant access to individual content URIs. These declarations do not establish which screen appears after USB insertion or whether opening an image passes a URI to HiGalleryL. REA did not resolve `SelectActivity.onCreate` from the inspected APK. No removable media was attached or opened for this check.

A separate package, NewLinkService, declares `UsbReceiver` for `MEDIA_MOUNTED`, `MEDIA_UNMOUNTED` and `MEDIA_EJECT`. REA shows that these volume events take different paths in `onReceive()`. On mount, if `newlink.usb_service` is already the string `1`, the receiver requests `UsbIntentService`; otherwise it sets the property to `1` without starting that service. The default on read is `0`, not a measurement of the value at boot. Unmount only logs; eject returns without requesting the service. This is a volume-mount handler, not evidence that plugging in any USB peripheral opens the file manager. No event was generated or property changed in this inspection.

The mount notification does not identify the volume the service will inspect. `getUsbPath()` enumerates `StorageManager.getVolumes()` and keeps replacing its result with the path of each mounted-readable volume whose type is `0`. If enumeration completes, it returns the last match in the returned list, or null if none matched. The method does not compare a volume with the mount intent URI or check its physical port. With multiple eligible volumes, the selected path therefore need not belong to the newly mounted one. This is static control flow, not an observed multi-drive test.

The mount path can do more than open a media browser. REA decoded `UsbIntentService.onHandleIntent()`: it obtains a path from `getUsbPath()`, lists its immediate children and passes each entry to a series of vendor handlers. Their names refer to boot media, network configuration, panel selection, keystone and motor tests, among other functions. This method establishes dispatch, not which handlers accept an entry or whether any change succeeds. For a read-only audit, inspect the stock service offline rather than inserting test media: insertion itself can invoke this path before a user selects a file.
